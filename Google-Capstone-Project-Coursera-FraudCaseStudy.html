The Ask Phase¶

After analyzing the dataset, I have identified the business task, stakeholders and the metric as seen below:
Business Task:
A fictional mobile payment company has noticed the rise of fraud in their services. They want to know which transaction types and behaviours carry the most risk of fraud so they can crack down on them and prevent them from happening again.
Stakeholders:
Head of Fraud Detection Department of the fictional mobile payment company, who will use these findings to see which fraud patterns to target. The Prepare Phase¶

The next phase is the prepare phase, where the task is to find data that is appropriate for this analysis, which I have already found with the PaySim dataset that is linked above. The dataset can be found in kaggle, where it is split into 11 columns:

  1. step - 1 unit of time in the real world where 1 step equals to 1 real hour.
  2. type - the transaction type.
  3. amount - the amount in the transaction.
  4. nameOrig -the name of the customer who started the transaction.
  5. oldbalanceOrg - initial balance before the transaction.
  6. newbalanceOrig - new balance after the transaction.
  7. nameDest - the name of customer who is the recipient of the transaction.
  8. oldbalanceDest - initial balance of the recipient before the transaction.
  9. newbalanceDest - new balance recipient after the transaction.
  10. isFraud - flags transactions made by fraudulent agents in the simulation.
  11. isFlaggedFraud - where the system flags a transaction as fraudulent.

In terms of data credibility, the dataset is synthetic so it may not perfectly reflect real-world behavior. Below is how the dataset is assessed against ROCCC:
Reliable: data generated is synthetic instead of pulling data from actual transactions so it may not reflect real world behaviors.
Original: it is a secondary source as it is obtained from kaggle as it is not collected first-hand.
Comprehensive: it has over 6 million rows with 11 columns, so the data is very detailed though it lacks date and time data types.
Current: since it was last updated 9 years ago, the data does not represent current trends.
Cited: it is licensed by CC BY-SA 4.0, which means I am free to use and adapt the source as long as the original source is provided. I have stated the source at the beginning of this jupyter notebook.

As seen in the code below, the data's integrity is verified by checking if they were any duplicate or null values, where none were found. I also checked if the values in the isFlaggedFraud and isFraud columns only contain 0 and 1 values to ensure that it only contain valid values as 2 values are needed to show if whether the transaction was flagged as true or false. It helps to answer my question as it can help to identify how fraud detection can be improved. The main problem with the data is that it is very big, having more than 6 million rows. Because of that, the data cannot be rendered in Excel, so the data had to be imported in a postgresql database, which will be touched upon more in the next phase. Other than the fact that the data is simulated instead of using actual data, 2 limitations to the dataset are fraudulent transactions make up around 0.13% of the total transactions and that it only occurs on cash-out and transfer transaction types. Finally, there is no date data type listed in this dataset, so I won't be able to analyze the fraud trends over time.

fraudTransactionFinding=pd.read_sql('SELECT ROUND(AVG(isFraud)*100,2), type FROM financial_analysis GROUP BY type',engine);
### Reason for this is because % sign does not work in the read sql function
fraudTransactionFinding.columns = ["Fraud rate (%)", "Transaction type"];
print(fraudTransactionFinding);

Now this is where I gather some findings. The first finding was to see the percentage of the transactions split by its type that were identified as fraud. As stated before, only cash_out and transfer types were found to include fraudulent transactions, with cash_out having around 0.18% while transfers have up to 4 times as many fraudulent transactions with almost 0.8%. For the second finding, the fraud flagging system is shown to accurately flag around 0.19% of the total fraudulent transactions as fraud, which is a critical vulnerability for the head of the fraud handling department, since this suggests that the logic behind the fraud flagging system needs to be improved, otherwise these fraudulent transactions won't be investigated by the team. Finally, the last finding is to identify if there was any relationship between fraudulent transactions and whether the account balance after the transaction has been made is 0. As seen in the output above, the result of legitimate transactions that result in an empty balance is more than 56%, while the result of fraudulent transactions that result in an empty balance is over 98%, which shows that fraudulent transactions are over 1.5 times more likely to empty their balance compared to legitimate transactions.
